> - 설계의 *배경과 당시 판단*은 [PRD 스냅샷](./prd/)에 남긴다. 이 문서는 "지금 무엇이 참인가"만 다룬다.

## 제1장 제품 정의

### §1.1 목적
모바일 청첩장을 비롯한 각종 초대장(돌잔치, 파티 등)을 **누구나 몇 분 안에** 만들고 링크로 공유할 수 있게 한다.

### §1.2 두 가지 시작 경로
사용자는 시작 시 둘 중 하나를 **스스로 선택**한다. 어느 경로로 시작하든 결과물은 동일한 `InvitationDoc`이며, 이후 편집기에서 세부 편집이 가능하다.

1. **쉽게 시작 (Quick Start)** — 사진 + 최소 정보만 입력하면 시스템이 틀(대표 사진·갤러리 배치·테마·색상)을 잡아준다. → 결과 확인 → 편집기로 이동.
2. **편집기에서 바로 시작** — 행사 종류의 기본 템플릿으로 편집기를 바로 연다.

### §1.3 지원 행사 종류 (`EventType`)
| 값 | 이름 | 주최자(host) 구성 |
|---|---|---|
| `wedding` | 결혼식 | 신랑, 신부 (2명) |
| `first-birthday` | 돌잔치 | 아기 (1명, 부모 = 혼주 자리) |
| `party` | 파티/모임 | 호스트 (1명) |

새 행사 종류 추가 시 `src/data/templates.ts`의 `EVENT_PRESETS`에만 정의를 추가한다. (§3.4)

### §1.4 범위 밖 (v0.1 기준)
홈(랜딩) 페이지 본 개발, 회원/로그인, 서버 저장, 결제, 실제 공유 URL 발급. → 로드맵(제10장).

## 제3장 데이터 모델

### §3.1 단일 문서 원칙
초대장 하나 = `InvitationDoc` 하나 (`src/types/invitation.ts`). 렌더러·편집기·저장소는 모두 이 타입만 주고받는다.

### §3.2 공통 사실(core)과 섹션 데이터의 분리
- **여러 섹션이 공유하는 사실**(주최자 이름·연락처·부모, 일시, 장소)은 `doc.core`에 **한 번만** 저장한다.
- 섹션의 `data`에는 **그 섹션에서만 쓰는 표현용 값**(문구, 레이아웃, 토글)만 둔다.
- 예: 히어로의 날짜, 달력 섹션의 날짜, 찾아오는 길의 장소는 모두 `core`를 읽는다. 날짜를 한 곳에서 고치면 전부 바뀐다.

### §3.3 이미지 참조
- 이미지는 `doc.images: Record<id, ImageAsset>`에 한 번 저장하고, 섹션은 **id로만 참조**한다.
- 참조되지 않는 이미지는 저장 시 정리하지 않는다(v0.1). 사용자가 갤러리에서 삭제하면 `images`에서도 제거한다.

### §3.4 템플릿
- 행사 종류별 기본 문서는 `createDoc(eventType)`이 만든다. 하드코딩된 기본값은 `src/data/templates.ts` 한 곳에만 둔다.
- 문서 스키마가 바뀌면 `doc.version`을 올리고 `migrateDoc()`에 마이그레이션을 추가한다.

## 제4장 섹션 정책

### §4.1 섹션 목록 (v0.1)
| type | 이름 | 사용하는 core | 섹션 고유 data |
|---|---|---|---|
| `hero` | 히어로(맨 위) | hosts, datetime, venue | 대표 사진, 레이아웃, 헤드라인 |
| `greeting` | 인사말(문구) | hosts(서명) | 제목, 본문 |
| `calendar` | 날짜 | datetime | 달력/카운트다운 표시 여부 |
| `gallery` | 갤러리 | — | 사진 id 목록, 레이아웃 |
| `parents` | 혼주(가족 안내) | hosts | 연락처 버튼 표시 여부 |
| `location` | 찾아오는 길 | venue | 교통편 안내, 지도 버튼 표시 |
| `account` | 마음 전하실 곳(계좌번호) | hosts(그룹 라벨) | 계좌 목록, 접기 여부 |
| `guestbook` | 신랑/신부에게 할 말 | hosts(대상 선택) | 제목, 안내 문구 |

### §4.2 섹션 규칙
1. **타입별 1개.** 같은 타입의 섹션은 문서에 최대 1개. 섹션은 삭제하지 않고 `enabled`로 숨긴다.
2. **히어로 고정.** `hero`는 항상 0번 위치이며 순서 이동·숨김 불가.
3. 나머지 섹션은 자유롭게 순서 변경(위/아래) 및 표시/숨김 가능.
4. 섹션은 `enabled=false`여도 데이터를 보존한다.
5. 새 섹션 타입 추가 절차: ① `SectionType`·data 타입 추가 → ② `templates.ts` 기본값 → ③ 렌더러 컴포넌트 → ④ 편집 폼 → ⑤ 이 표 갱신.

### §4.3 계좌번호 정책
- 계좌는 주최자 그룹(신랑측/신부측 등)별로 묶어 보여준다.
- 하객 화면에서는 기본 **접힘** 상태, 펼친 뒤 "복사" 버튼으로 `은행 계좌번호` 형태를 클립보드에 복사한다.
- 계좌번호는 입력한 그대로 표시한다(마스킹하지 않음 — 송금 목적상 전체 노출 필요).

### §4.4 "신랑/신부에게 할 말" 정책
- v0.1은 서버가 없으므로 메시지는 **보는 사람의 브라우저(localStorage)** 에만 저장되는 데모 동작이다.
- 대상(받는 사람)은 `core.hosts` 중 선택. 이름 20자, 내용 300자 제한.
- 서버 도입 시 비밀글/관리자 삭제 정책을 새 PRD로 정의한다.

### §4.5 찾아오는 길 정책
- v0.1은 지도 임베드 없이 **외부 지도 앱 링크**(카카오맵·네이버지도·티맵)를 주소 검색어로 연다. (API 키 불필요)
- 주소 복사 버튼을 제공한다.

## 제5장 쉽게 시작(Quick Start) 알고리즘

> 규칙 기반 v1. 결과는 항상 "출발점"이며 편집기에서 모두 바꿀 수 있어야 한다.

### §5.1 입력
- 사진 1~20장 (필수 1장 이상), 행사 종류, 주최자 이름, 일시, 장소명/주소(선택).

### §5.2 사진 분석 (`src/lib/image.ts`)
각 사진을 32×32로 축소해 계산:
- `aspect` = 너비/높이
- `luminance` = 평균 밝기 (0~1)
- `color` = 채도 가중 평균색(무채색 사진은 평균색)

### §5.3 대표(히어로) 사진 선택 점수
```
score = 세로형 적합도(aspect 0.6~0.85 → 1.0, 세로 0.5, 정방 0.3, 가로 0)
      + 밝기 적합도 (1 - |luminance - 0.55| * 1.5, 최소 0)
      + 업로드 순서 가산 (첫 장 0.3, 이후 0)
```
최고점 사진이 히어로. 동점이면 먼저 올린 사진.

### §5.4 배치 규칙
- 히어로 레이아웃: 히어로 사진이 세로형이면 `full`(전체 화면), 아니면 `frame`(액자형).
- 갤러리: 히어로를 **제외한** 나머지 사진, 업로드 순서 유지. 나머지가 0장이면 갤러리 섹션 숨김.
- 갤러리 레이아웃: 6장 이상 `grid`, 미만 `slide`.

### §5.5 테마 추천
히어로 사진 색(HSL) 기준:
- 채도 < 0.15 → `modern` (무채색 사진)
- 색상 330~360° 또는 0~30° 이고 밝기 > 0.55 → `romantic`
- 그 외 → `classic`

포인트 컬러(accent) = 히어로 색의 색상(hue) 유지, 채도 35~55%, 명도 38~45%로 보정(흰 배경 대비 확보). 무채색이면 프리셋 기본 accent.

### §5.6 결과 화면
추천 결과를 미리보기로 보여주고 테마 프리셋 3종을 즉시 바꿔볼 수 있게 한다. "편집기에서 다듬기"를 누르면 저장 후 `/editor`로 이동.

## 제6장 편집기 정책

### §6.1 레이아웃 (반응형)
| 뷰포트 | 구성 |
|---|---|
| 데스크탑 ≥ 1024px | 3단: 섹션 목록(260px) │ 속성 편집(가변) │ 휴대폰 미리보기(고정 폭 390px, sticky) |
| 태블릿 768~1023px | 2단: [섹션 목록 + 속성 편집 세로 배치] │ 미리보기 |
| 모바일 < 768px | 1단 + 하단 탭바 `구성 / 편집 / 미리보기`. 한 번에 한 패널만 표시 |

- 모바일에서 섹션을 고르면 자동으로 `편집` 탭으로 이동한다.
- 미리보기에서 섹션을 탭/클릭하면 해당 섹션이 선택된다(모바일은 편집 탭으로 이동).

### §6.2 편집 대상
- `문서 설정`(행사 종류 제외한 공통 정보 = core), `테마`, 각 섹션 data.
- 행사 종류는 생성 후 변경 불가(v0.1). 바꾸려면 새로 시작.

### §6.3 실시간 반영
모든 입력은 즉시 미리보기에 반영된다. 미리보기 렌더러는 하객 화면(`/view`)과 **같은 컴포넌트**를 쓴다. (WYSIWYG 보장)

### §6.4 상태 관리
- `EditorProvider`(useReducer) 하나가 문서 상태를 소유. 모든 변경은 액션(`src/store/editorReducer.ts`)을 통해서만.
- 리듀서는 §4.2 규칙(히어로 고정, 타입별 1개)을 **강제**한다. UI가 실수해도 규칙이 깨지지 않는다.

## 제7장 저장 정책

### §7.1 v0.1: 로컬 초안
- 저장소: 브라우저 **IndexedDB** (`invitation-maker` DB, `drafts` 스토어). 이미지(data URL) 크기 때문에 localStorage 대신 IndexedDB 사용.
- 슬롯: 초안 1개 (`current`). 새로 시작하면 덮어쓴다 — 기존 초안이 있으면 시작 화면에서 확인을 받는다.
- 자동 저장: 마지막 변경 후 **600ms 디바운스**. 상단에 `저장 중… / 저장됨 / 저장 실패` 표시.

### §7.2 이미지 정책
- 업로드 시 긴 변 **1600px**, JPEG 품질 **0.82**로 재인코딩(EXIF 회전은 브라우저 `createImageBitmap` 기본 동작에 따름).
- 허용 형식: `image/*` (HEIC는 브라우저가 디코딩 가능한 경우만).
- 1회 업로드 최대 20장, 문서당 최대 30장.

## 제8장 UI·접근성 공통 규칙

- 앱 UI 폰트: Noto Sans KR. 초대장 폰트: 테마의 `font`(serif=Gowun Batang / sans=Noto Sans KR).
- 터치 타깃 최소 44×44px. 모든 아이콘 버튼에 `aria-label`.
- 색만으로 상태를 표시하지 않는다(텍스트 병기).
- 초대장 본문 최대 폭 480px, 중앙 정렬 (데스크탑에서 열어도 모바일 비율 유지).
- `prefers-reduced-motion`이면 애니메이션 제거.

## 제9장 개발 규칙

### §9.1 기술 스택
React 18 + TypeScript + Vite, 라우팅 react-router-dom v6. 스타일은 CSS 파일 + CSS 변수(외부 UI 라이브러리 미사용).

### §9.2 디렉터리
```
src/
  types/        도메인 타입 (InvitationDoc 등)
  data/         템플릿·프리셋 기본값
  store/        편집기 상태(리듀서, 컨텍스트, 자동저장)
  lib/          순수 로직 (이미지 분석, 쉽게시작, 날짜, 저장소)
  components/
    invitation/ 초대장 렌더러 + 섹션 컴포넌트 (편집기·뷰어 공용)
    editor/     편집기 전용 UI
    common/     공용 UI
  pages/        라우트 단위 화면
```

### §9.3 커밋 메시지
```
<type>(<scope>): <한 줄 요약>

<주요 내용 — 무엇을, 왜. 글머리표 권장>

Refs: PRD-XXXX, §조항
```
- type: `feat` `fix` `docs` `refactor` `style` `chore` `test`
- 정책을 바꾸면 본문에 **바뀐 조항**과 이전→이후를 적는다.

### §9.4 문서 갱신 의무
- 정책·로직 변경 → 이 문서 해당 조항 수정 + 개정 이력 추가 (같은 커밋)
- 의미 있는 기능 설계 → 새 PRD 스냅샷 작성

## 제10장 로드맵 (참고)
1. 홈(랜딩) 페이지
2. 백엔드 저장 + 공유 URL 발급 + OG 메타(카카오톡 공유 썸네일)

6. 실행 취소/다시 실행, 다중 초안
