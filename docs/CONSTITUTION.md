## 제1장 제품 정의

### §1.1 목적
**모바일 청첩장**을 누구나 몇 분 안에 만들고 링크로 공유할 수 있게 한다. (v0.2부터 결혼식 전용 — §1.3)

### §1.2 전체 흐름: 템플릿 → 시작 방법 → 편집기
1. **템플릿 선택** — 디자인 템플릿(§3.5) 하나를 고른다. 모든 흐름의 시작점이다.
   - 목록에서 카드를 누르면 **템플릿 미리보기** 화면으로 간다. 샘플 청첩장을 끝까지 스크롤해 본 뒤 `이 템플릿으로 시작하기`로 다음 단계에 간다. (목록 화면에는 시작 버튼이 없다)
2. **시작 방법 선택** — 사용자가 **스스로** 둘 중 하나를 고른다. 이 화면에는 선택한 템플릿 정보를 표시하지 않는다(템플릿은 헤더 `←`로 다시 고른다).
   - **쉽게 시작 (Quick Start)** — 한 페이지에서 기본 정보와 사진을 입력하면, 고른 템플릿 위에 사진을 배치해(대표 사진·갤러리) 바로 편집기로 간다. 모든 항목은 비워도 된다.
   - **바로 편집** — 고른 템플릿을 내용 없이 그대로 편집기에서 연다.
3. **편집기** — 어느 경로로 왔든 결과물은 동일한 `InvitationDoc`이며 모든 항목을 세부 편집할 수 있다.

- 각 단계에서 이전 단계로 돌아갈 수 있다(시작 방법 → 템플릿 변경, 편집기 → 시작 방법).

### §1.3 대상 행사: 결혼식 전용
- 지원 행사는 **결혼식 하나**다. 사용자에게 행사 종류를 묻는 분기(선택 화면)는 두지 않는다.
- 주최자(host)는 항상 `신랑`, `신부` 2명이며 이 순서를 유지한다.
- 문서에는 `eventType: 'wedding'` 필드를 그대로 둔다(저장 스키마 유지·향후 확장 여지). 코드에서 이 값으로 분기하지 않는다.
- 다른 행사(돌잔치·파티 등)를 다시 지원하려면 새 PRD로 결정한 뒤 이 조항을 개정한다.

### §1.4 범위 밖 (v0.4 기준)
홈(랜딩) 페이지, **저장·이어서 편집**(§7.1), 결혼식 외 행사(돌잔치·파티 등), 회원/로그인, 서버 저장, 결제, 실제 공유 URL 발급. → 로드맵(제10장).

## 제2장 화면 구성 및 라우팅

| 경로 | 화면 | 비고 |
|---|---|---|
| `/` | — | `/templates`로 리다이렉트 (홈은 범위 밖) |
| `/templates` | ① 템플릿 목록 | 카드 클릭 → `/templates/<id>` |
| `/templates/<id>` | ①-a 템플릿 미리보기 | 샘플 청첩장(하객 화면 모드) + 하단 `이 템플릿으로 시작하기` → `/start?template=<id>`. 잘못된 id는 `/templates`로 |
| `/start?template=<id>` | ② 시작 방법 선택 | 쉽게 시작 / 바로 편집. 헤더 `←`는 `/templates/<id>`. 템플릿 id가 없거나 잘못되면 `/templates`로 |
| `/quick?template=<id>` | ②-a 쉽게 시작 | 한 페이지(기본 정보 + 사진) → `편집 시작하기` → `/editor`. 템플릿 없으면 `/templates`로 |
| `/editor` | ③ 편집기 | 문서가 없으면(새로고침 등) `/templates`로 |
| `/view` | 미리보기(하객 시점) | 문서가 없으면 `/templates`로 |

## 제3장 데이터 모델

### §3.1 단일 문서 원칙
초대장 하나 = `InvitationDoc` 하나 (`src/types/invitation.ts`). 렌더러·편집기는 모두 이 타입만 주고받는다.

### §3.2 공통 사실(core)과 섹션 데이터의 분리
- **여러 섹션이 공유하는 사실**(주최자 이름·연락처·부모, 일시, 장소)은 `doc.core`에 **한 번만** 저장한다.
- 섹션의 `data`에는 **그 섹션에서만 쓰는 표현용 값**(문구, 레이아웃, 토글)만 둔다.
- 예: 히어로의 날짜, 달력 섹션의 날짜, 찾아오는 길의 장소는 모두 `core`를 읽는다. 날짜를 한 곳에서 고치면 전부 바뀐다.

### §3.3 이미지 참조
- 이미지는 `doc.images: Record<id, ImageAsset>`에 한 번 저장하고, 섹션은 **id로만 참조**한다.
- 참조되지 않는 이미지는 저장 시 정리하지 않는다(v0.1). (편집기에서 대표 사진을 바꿔도 이전 사진은 "올린 사진"으로 남아 다시 고를 수 있다.)
- 갤러리에서 사진을 삭제하면, 다른 섹션(히어로)이 참조하지 않는 경우에만 `images`에서도 제거한다. 참조 중이면 갤러리 목록에서만 뺀다.

### §3.4 기본 문서
- 기본 문서는 `createDoc()`이 만든다. 청첩장 기본 문구·구성(`WEDDING`) 등 하드코딩된 기본값은 `src/data/templates.ts` 한 곳에만 둔다.
- `doc.version`은 유지한다. 저장 기능이 다시 생기면(§7.1) 스키마 변경 시 마이그레이션을 함께 도입한다.

- `applyTemplate(doc, t)`는 위 디자인 값만 덮어쓰고 **내용(이름·날짜·장소·사진·문구 본문)은 건드리지 않는다**. 문서에 `templateId`를 기록한다.
- 템플릿 카드 썸네일과 템플릿 미리보기 화면은 모두 실제 렌더러(`InvitationView`)로 **샘플 청첩장**(`src/data/sampleDoc.ts`)을 그린다. 별도 썸네일 이미지를 두지 않는다.
  - 샘플 청첩장은 **모든 섹션이 채워진 상태**다: 샘플 이름·부모님·장소·교통편·계좌(`000-0000-0000`), 대표(히어로) 사진은 실제 웨딩 샘플 사진(`src/assets/samples/wedding-hero-01.jpg`, 모든 템플릿 공통), 갤러리 6장은 템플릿 색의 그라데이션 자리 사진.
  - **샘플 사진 보관:** 사용자가 대화로 준 샘플 이미지는 `src/assets/samples/`에 `<용도>-<번호>.jpg`(예: `wedding-hero-01.jpg`)로 저장하고 코드에서 `import`한다(Vite가 배포 경로·캐시 이름을 처리). 용량을 줄이려 JPG(품질 85)로 변환한다. 레포가 공개이므로 공개해도 되는 사진만 넣는다.
  - 미리보기 화면은 데스크탑에서 휴대폰 프레임, 모바일에서는 프레임 없이 전체 폭으로 보여준다.
- **디자인은 템플릿이 전적으로 결정한다.** 편집기는 테마·글꼴·색·레이아웃을 편집하지 않는다(§6.2). 사용자는 정보 입력에만 집중한다.
- 디자인을 바꾸려면 템플릿을 다시 고른다(편집기 내 템플릿 변경은 미정 — PRD-0005 열린 질문).

### §3.6 템플릿 디자인 시스템 (PRD-0017, PRD-0018)
- **템플릿 = 계열(family) + 팔레트(palette) + 모양(shape)** (+ 히어로·갤러리·예식 일자 레이아웃). 정의: `src/data/designSystem.ts`, 토큰 주입: `src/components/invitation/theme.tsx`.
- **계열** `Theme.family`: `basic`(기본, 2~6번) / `editorial`(에디토리얼, 1번). 렌더러 루트에 `.inv--fam-<family>`. 계열 CSS는 **토큰으로만** 쓴다 — 색 값을 직접 쓰지 않는다. 계열이 정하는 것: 포인트 바탕 섹션(섹션 문맥 토큰 반전), 디스플레이 글꼴.
- **팔레트** `Theme.preset` → `THEME_PRESETS`(`bg`·`surface`·`text`·`muted`·`accent`·`band`·`onBand`·`paper`·`board`) → CSS 변수 `--inv-*`. 렌더러 색은 이 중 **`--inv-accent`(포인트)·`--inv-text`(잉크)·`--inv-bg`(크림) 세 가지에서만** 파생한다.
- **모양** `Theme.shape`: `round` = control `999px`(알약)·card `20px`·paper `8px`·media `0` / `square` = 모두 `0`. CSS 변수 `--inv-r-control`·`--inv-r-card`·`--inv-r-paper`·`--inv-r-media`.
- 계열 글꼴 토큰 `--inv-font-title`·`--inv-font-display`(basic은 테마 글꼴, editorial은 Oblata Display).

### §4.2 섹션 규칙
1. **타입별 1개.** 같은 타입의 섹션은 문서에 최대 1개. 섹션은 삭제하지 않고 `enabled`로 숨긴다.
2. **고정 섹션.** `hero`는 항상 맨 앞, `brand`는 항상 맨 뒤. 둘 다 순서 이동·숨김 불가(`isPinned`). 다른 섹션도 두 고정 자리로는 들어갈 수 없다. 리듀서(`normalizeSections`, `REORDER_SECTION`, `TOGGLE_SECTION`)가 강제한다.
3. 나머지 섹션은 자유롭게 순서 변경(드래그 앤 드롭, §6.7) 및 표시/숨김 가능.
4. 섹션은 `enabled=false`여도 데이터를 보존한다.
5. 새 섹션 타입 추가 절차: ① `SectionType`·data 타입 추가 → ② `templates.ts` 기본값·`SECTION_ORDER`·라벨 → ③ 렌더러 컴포넌트 → ④ 편집 폼 → ⑤ 모바일 편집 버튼 문구 → ⑥ 이 표 갱신.

### §4.3 계좌번호 정책
- 계좌는 주최자 그룹(신랑측/신부측 등)별로 묶어 보여준다.
- 하객 화면에서는 기본 **접힘** 상태, 펼친 뒤 "복사" 버튼으로 `은행 계좌번호` 형태를 클립보드에 복사한다.
- 계좌번호는 입력한 그대로 표시한다(마스킹하지 않음 — 송금 목적상 전체 노출 필요).

### §4.4 방명록 정책
- 섹션 이름은 `방명록`(기본 제목도 `방명록`).
- **보기 우선:** 섹션은 남겨진 메시지를 먼저 보여준다. 쪽지를 3열 **9개씩** 놓고(가장자리 가까이까지), 넘치면 페이지 번호로 넘긴다. 정렬: 내가 남긴 것(최신순) → 예시 쪽지(최신순).
  - 쪽지(종이 `--sec-paper`: 포인트 바탕 섹션에선 크림, 그 밖엔 잉크 4%, 라운드 8, 3:4, 그림자 없음): 작성자(13 Medium 포인트) · 구분선 · 본문(최대 3줄) · 날짜(잉크 60%). 기울기는 메시지 id로 정해져 매번 같다.
  - 쪽지를 누르면 **상세 모달**: 작성자(17 SemiBold 포인트) · 구분선 · 본문 전체(17) · 날짜 · `삭제` 칩. 닫기는 배경을 누른다(`배경 눌러서 닫기`).
- **작성은 `방명록 남기기` 버튼으로만** 연다(작성 모달: 제목 · 성함 · 내용(`0/300`) · 비밀번호(`삭제할 때 필요해요.`) · `남기기`). 섹션 안 버튼은 `inverse`(크림 바탕). 하객 화면(`/view`)에서는 섹션이 화면에 보이는 동안 하단에 떠 있는 버튼, 편집기·템플릿 미리보기에서는 섹션 안 버튼(§3.6 `floatingActions`).
- 서버가 없으므로 메시지는 **보는 사람의 브라우저(localStorage, `guestbook:<docId>`)** 에만 저장되는 데모 동작이다.
- **받는 사람(신랑/신부)은 고르지 않는다.** 방명록은 두 사람 모두에게 남기는 것이다.
- 입력: 이름(20자), **비밀번호(필수, 4~20자)**, 내용(300자).
- **삭제:** 상세 모달에서 `삭제` → `작성 시 입력한 비밀번호` 입력칸이 열리고 다시 `삭제`를 눌러 확인한다. 틀리면 `비밀번호가 올바르지 않습니다.`(포인트색).
- 비밀번호는 원문을 저장하지 않고 메시지 id를 섞은 해시(`GuestMessage.pw`, `src/lib/guestbook.ts`)만 저장한다. 브라우저 저장소 데모라 보안 장치는 아니며, 서버 도입 시 서버에서 해시·검증한다.
- 예시 쪽지 `GuestbookData.seed`는 샘플 청첩장(템플릿 미리보기)에만 넣는다(11개, 비밀번호 `0000`). 사용자 문서에는 넣지 않는다. 예시 쪽지를 지우면 그 화면에서만 숨긴다.
- 서버 도입 시 비밀글/관리자 삭제 정책을 새 PRD로 정의한다.

### §4.6 갤러리(사진 모음) 정책
- 갤러리는 기본 구성 섹션이며 **기본으로 켜져 있다.** 사진이 없다는 이유로 자동으로 숨기지 않는다(사용자가 섹션이 없다고 오해하지 않도록).
- 사진이 0장일 때:
  - 편집기 미리보기: 빈 칸 6개(+)와 "갤러리 편집에서 사진을 추가해 주세요" 안내를 보여주고, `갤러리 편집`으로 바로 사진을 넣을 수 있다.
  - 하객 화면(`/view`·발행본): 섹션을 그리지 않는다.
- 사진은 3열 정사각 격자(크림 테두리 4px). 하객 화면에서 사진을 누르면 라이트박스(흐린 배경 · 테두리 사진 · 좌우 셰브론 · `배경 눌러서 닫기`)로 크게 보고 좌우로 넘긴다.


### §4.7 참석 여부(RSVP) 정책
- 하객 입력: 어느 측(신랑측/신부측), 성함(필수, 20자), 참석/불참, 참석 시 인원(본인 포함 1~10명, 질문 켬일 때), 참석 시 식사 여부(식사함/안 함/미정, 질문 켬일 때).
- 어느 측은 카드형 선택(`신랑` 작은 레이블 + 이름), 나머지는 알약 선택. 참석 인원은 `Stepper`(입력칸 모양, − 왼쪽 · + 오른쪽 포인트색 아이콘, 끝값 비활성). 안내 문구 기본값은 비움.
- 제출하면 "○○님, N명 참석으로 전달되었어요" 확인 화면, `다시 보내기`로 수정.
- 서버가 없으므로 응답은 **응답한 사람의 브라우저에만** 저장된다(데모). 서버 도입 시 주최자용 응답 모아보기·집계·마감일을 새 PRD로 정의한다.

### §4.8 게스트 스냅 정책
- 하객이 예식 날 찍은 사진을 올리는 공간. **필요한 사람만 켜는 섹션이라 기본 꺼짐.**
- 한 번에 최대 10장. 서버가 없으므로 올린 사진은 그 화면에만 잠깐 보이고 저장되지 않는다(데모). 서버 도입 시 공개 시점(예: 예식 당일부터), 용량, 주최자 다운로드를 새 PRD로 정의한다.

### §4.9 브랜드 소개 정책
- 청첩장 맨 아래에 항상 표시되는 **홍보 배너 자리**. 배너가 준비될 때까지 `홍보 배너 영역` 문구만 둔다(로고·소개·링크 없음).
- **순서 변경·숨김·편집 불가.** 섹션 목록에 `고정` 배지만 보이고 손잡이·스위치가 없다. 모바일 미리보기에 `[섹션 편집]` 버튼이 없다. 편집 패널은 "편집할 수 없어요" 안내만.
- 배너를 넣을 때 링크는 하객 화면에서만 이동하고 편집기 미리보기에서는 이동하지 않는다.


### §4.10 붙이기(스티커) 정책
> 청첩장 꾸미기는 두 축이다: **[섹션 편집]**(내용) + **[붙이기]**(내 사진 스티커로 장식).

- **붙이기 (바로 붙고 바로 이동):**
  1. `붙이기`를 누르면 그 자리에서 **기기 사진 선택 창을 바로** 연다. 선택 창을 닫으면 아무 일도 없다.
  2. 사진을 고르는 즉시 스티커가 **해당 섹션 가운데에 붙고 선택된 상태**가 된다(기본값: 하트·스티커·뿅뿅·보통, 사진 조정 없음). 단계 화면·시트는 없다.
  3. 선택된 상태에서 바로 끌어서 위치를 옮긴다. `완료`로 선택 해제.
- **붙은 스티커 선택 (꾸미기):** 편집기 미리보기에서 스티커를 누르면 선택되고, 하단 바에서
  - 탭 `프레임`(원·네모·하트·별·클로버, 내 사진이 잘린 모습으로) · `종류`(아래) · `크기`(작게·보통·크게) · `움직임`(없음·뿅뿅·둥실·빙글·두근·흔들, 움직이는 미리보기)
  - 선택 박스 테두리 아래 **`사진 조정`** 버튼 → 사진 조정 에디터(아래).
  - 선택된 동안 끌기·섹션 탭으로 위치 이동, `떼기`(삭제), `완료`(선택 해제).
  - **모든 변경은 즉시 문서에 반영**된다(취소 없음, 미리보기가 곧 결과). 다른 스티커를 누르면 선택이 그쪽으로 넘어간다.
- **종류(재질 효과):** `기본`(그림자만) · `스티커`(모양을 따라 흰 칼선 테두리) · `마스킹 테이프`(반투명 종이테이프 두 조각, 끝은 지그재그) · `골판지`(같은 모양의 골판지 판 위에 사진) · `폴라로이드`(아래 여백이 넓은 흰 카드 안 정사각 사진). 옵션은 내 사진에 각 효과를 입힌 미리보기로 보여준다.
- **사진 조정 에디터:** 선택한 **프레임 안에서** 사진의 크기·위치를 조절한다.
  - 화면: 전체 화면 어두운 배경, 가운데 프레임(무대 너비 72%) 모양만 뚫리고 **프레임 밖 사진은 검은 dim**으로 보인다.
  - 조작: 끌기 = 이동, 두 손가락(핀치)·마우스 휠·아래 막대 = 확대(1~3배). `처음 상태로`, `취소`(변경 버림), `완료`(반영).
  - 프레임에 빈틈이 생기지 않도록 이동 범위를 제한한다(사진이 항상 프레임을 덮음, `clampCrop`).
  - 사진의 기본 크기는 프레임을 꽉 채우는 크기(cover)이고, 조정값은 모든 종류·프레임에 공통으로 적용된다.
- **데이터:** `doc.stickers: Sticker[]` — `sectionId`, `imageId`, `shape`, `kind`, `crop`(`scale` 1~3, `ox`·`oy` 프레임 대비 %), `motion`, `size`, `x`·`y`(섹션 기준 중심 좌표 %, 0~100). 사진은 `doc.images`에 들어가며 문서당 30장 제한(§7.2)에 포함된다.
- **레이어:** 스티커는 섹션 안이 아니라 **청첩장 최상단 오버레이**(`StickerOverlay`)에 그린다. 섹션 경계에서 잘리지 않고 이웃 섹션 위로 걸칠 수 있다. 청첩장 바깥 가장자리(좌우·위아래)에서만 잘린다(가로 스크롤 방지).
  - 위치는 섹션 기준이다: 섹션의 레이아웃 위치(`offsetTop/Left/Width/Height`)를 재서 겹쳐 그리고, 높이가 바뀌면(`ResizeObserver`) 다시 잰다. 섹션 순서를 바꾸면 함께 움직이고, 섹션을 숨기면 함께 숨는다.
  - 중심은 섹션 안(0~100%)으로 제한 → 스티커 크기의 절반까지 섹션 밖으로 나올 수 있다.
  - 쌓임 순서: 섹션 내용 < 위치 정하기 영역 < 스티커 < `[섹션 편집]`/`[붙이기]` 버튼. 갤러리 라이트박스는 `body`로 포털해 스티커보다 위에 뜬다.
  - 하객 화면에서는 섹션처럼 화면에 들어올 때 나타난다(reduced-motion이면 바로 표시).
- **제한:** 섹션당 최대 5개. 브랜드 소개(§4.9)에는 붙일 수 없다. 리듀서(`ADD_STICKER`)가 강제한다.
- **크기:** 섹션 너비 대비 18% / 26% / 36%. 모양은 SVG 마스크로 사진을 잘라 만든다(사진 원본은 그대로).
- **위치 이동:** 선택된 스티커를 끌거나, 그 섹션 아무 곳을 누르면 그 자리로 이동. 키보드는 방향키로 2%씩. 끌기는 스티커에서만 받아서(터치 스크롤 유지) 화면 스크롤과 충돌하지 않게 한다.
- **꾸미기 UI (기기별):**
  - 모바일: 스티커가 선택된 동안 [섹션 편집]/[붙이기] 버튼과 하단 툴바를 숨기고, 화면 아래 떠 있는 **스티커 바**(탭 `프레임·종류·크기·움직임`, 한 번에 한 종류) + `떼기`·`완료`.
  - 데스크탑: 스티커를 선택하면 편집 패널이 **그 스티커의 섹션**으로 바뀌고(타이틀 = 섹션 이름 + `스티커 꾸미기` 배지), **타이틀 아래 내용이 스티커 꾸미기로 교체**된다 — `프레임`·`종류`·`크기`·`움직임`을 모두 펼쳐 보여주고 `떼기`·**`붙이기 완료`**. `사진 조정`은 패널에 두지 않고 미리보기의 선택 박스 아래 버튼으로만 연다(중복 제거). 섹션 표시 스위치는 숨긴다.
  - 데스크탑 `붙이기 완료`(또는 목록에서 다른 항목 선택) → 선택 해제, 원래 섹션 편집 정보로 복귀.
- **사진 삭제와의 관계:** 사진이 삭제되면 그 사진을 쓰는 스티커도 함께 제거된다. 갤러리에서 사진을 뺄 때 히어로나 스티커가 쓰는 사진이면 갤러리 목록에서만 빼고 사진은 남긴다(§3.3).
- **하객 화면:** 스티커는 장식이라 누를 수 없고(아래 버튼·링크를 가리지 않음), 모션은 계속 반복된다. `prefers-reduced-motion`이면 모션을 끈다.
- **진입점:** 모바일은 활성 섹션 위 `[섹션] 편집` 옆 `[붙이기]` 버튼(§6.5-3), 데스크탑은 편집 패널 **타이틀 바로 옆** `붙이기` 버튼. 두 곳 모두 같은 붙이기 아이콘(웃는 얼굴 + 더하기, `StickerPlusIcon`)을 쓴다. 붙은 뒤 선택·이동은 미리보기에서.
- **사진 바꾸기:** 별도 기능 없음. 떼고 새로 붙인다.

## 제5장 쉽게 시작(Quick Start) 알고리즘

> 규칙 기반 v1. 결과는 항상 "출발점"이며 편집기에서 모두 바꿀 수 있어야 한다.

### §5.1 입력
- 선택한 템플릿(필수). 그 외 신랑·신부 이름, 일시, 장소명, 주소, 사진(0~20장)은 **모두 선택**이다.
- **한 페이지**로 구성한다. 제목 `기본 정보를 입력해주세요`, 설명 `비워둬도 괜찮아요. 편집기에서 채울 수 있어요.`
- 입력 순서: 신랑·신부 이름 → 일시 → 장소 이름 → 주소 → 사진. 사진을 올리면 추천 대표 사진에 `대표` 표시.
- 하단 고정 `편집 시작하기` → 문서 생성 후 `/editor`. (결과 확인 화면 없음)

### §5.2 사진 분석 (`src/lib/image.ts`)
각 사진을 32×32로 축소해 계산:
- `aspect` = 너비/높이
- `luminance` = 평균 밝기 (0~1)
- `color` = 채도 가중 평균색(무채색 사진은 평균색)

### §5.3 대표(히어로) 사진 선택 점수
```
score = 세로형 적합도(aspect 0.6~0.85 → 1.0, 세로 0.5, 정방 0.3, 가로 0)
      + 밝기 적합도 (1 - |luminance - 0.55| * 1.5, 최소 0)
      + 업로드 순서 가산 (첫 장 0.3, 이후 0)
```
최고점 사진이 히어로. 동점이면 먼저 올린 사진.

### §5.4 역할 분담: 디자인은 템플릿, 사진 배치는 쉽게 시작
- 테마·글꼴·색·히어로/갤러리 레이아웃은 **템플릿 값을 그대로** 쓴다. 쉽게 시작이 덮어쓰지 않는다.
- 히어로 사진: §5.3 점수 최고점 사진.
- 갤러리: 히어로를 **제외한** 나머지 사진, 업로드 순서 유지. 나머지가 0장이어도 갤러리 섹션은 **켜 둔다**(§4.6).

### §5.5 사진이 없을 때
- 사진을 올리지 않으면 대표 사진은 비어 있고(빈 자리 안내 표시), 갤러리는 빈 상태로 켜져 있다(§4.6). 편집기에서 추가할 수 있다.

## 제6장 편집기 정책

### §6.1 레이아웃 (반응형)
| 뷰포트 | 구성 |
|---|---|
| 데스크탑 ≥ 1024px | 3단: 섹션 목록(260px) │ 속성 편집(가변) │ 휴대폰 미리보기(고정 폭 390px, sticky) |
| 태블릿 768~1023px | 2단: [섹션 목록 + 속성 편집 세로 배치] │ 미리보기 |
| 모바일 < 768px | **미리보기 전체 화면 + 바텀시트 편집** (탭으로 나누지 않음). 상세는 §6.5 |

- 데스크탑·태블릿: 미리보기에서 섹션을 클릭하면 해당 섹션이 선택되고 속성 편집 패널이 바뀐다.
- 모바일/데스크탑 분기 기준은 CSS와 동일한 `max-width: 767px` (JS `matchMedia`로 판정, 화면 회전 시 즉시 전환).

### §6.2 편집 대상
- `기본 정보`(core)와 각 섹션의 **내용**(문구·사진·표시 여부·순서)만 편집한다.
- **디자인 편집 없음:** 테마 패널, 히어로 사진 배치(full/frame/arch), 갤러리 보기 방식(grid/slide) 선택을 두지 않는다. 모두 템플릿 값을 따른다(§3.5).
- 용어: core 편집 화면의 이름은 데스크탑·모바일 모두 `기본 정보`.

### §6.3 실시간 반영
모든 입력은 즉시 미리보기에 반영된다. 미리보기 렌더러는 하객 화면(`/view`)과 **같은 컴포넌트**를 쓴다. (WYSIWYG 보장)

### §6.4 상태 관리
- `EditorProvider`(useReducer) 하나가 문서 상태를 소유. 모든 변경은 액션(`src/store/editorReducer.ts`)을 통해서만.
- 리듀서는 §4.2 규칙(히어로 고정, 타입별 1개)을 **강제**한다. UI가 실수해도 규칙이 깨지지 않는다.

### §6.5 모바일 편집 (미리보기 우선 + 바텀시트)
> 참고: Apple 초대장(Invites) 앱의 "배경 편집 → 바텀시트" 패턴.

1. **기본 화면 = 미리보기.** 초대장이 전체 화면으로 보이고, 사용자는 스크롤로 섹션을 둘러본다. 구성/편집/미리보기 탭을 두지 않는다.
2. **활성 섹션.** 화면 세로 중앙선에 걸친 섹션이 활성 섹션이다. 섹션을 탭해도 활성 섹션이 된다. 활성 섹션은 옅은 점선 테두리로 표시한다.
3. **[섹션 편집] + [붙이기] 버튼.** 활성 섹션 위, 화면 중앙에 `<섹션> 편집` 알약 버튼과 그 옆 `붙이기` 버튼(§4.10)을 함께 띄운다(예: `대표 사진 편집`, `시작 멘트 편집`, `추가 정보 편집`. 브랜드 소개는 버튼 없음). 섹션 안에서 sticky로 따라다니며 섹션 경계를 벗어나지 않는다. 비활성 섹션의 버튼은 숨기고 포커스 대상에서 제외한다.
4. **바텀시트.** 버튼을 누르면 해당 섹션의 편집 항목이 바텀시트로 열린다. 시트는 내용 높이만큼(최대 화면 88%) 올라오며, 뒤의 미리보기는 실시간으로 바뀐다. 고정 섹션(히어로·브랜드 소개)을 제외한 섹션은 시트 상단에 `초대장에 표시` 토글을 둔다.
5. **시트 닫기.** ✕ 버튼, 배경 탭, Esc, 헤더를 아래로 110px 이상 끌기. 시트가 열려 있는 동안 페이지 스크롤은 잠근다.
6. **공통 도구.** 상단: 공통 헤더(§8) — 좌측 `미리보기`(→ `/view`), 중앙 로고, 우측 `청첩장 만들기`(§6.6). 닫기(✕) 버튼 없음. 하단 플로팅 툴바: `구성`(섹션 순서·표시 시트, 기본 정보 항목은 제외) · `기본 정보`. (공유 버튼 없음)
7. `구성` 시트에서 섹션을 고르면 미리보기가 그 섹션으로 스크롤되고 해당 섹션 편집 시트로 바뀐다.
8. 숨긴 섹션은 미리보기에 없으므로 `구성` 시트에서만 다시 켤 수 있다.

### §6.6 청첩장 만들기 (제목·링크)
- 진입: 편집기 헤더 우측 `청첩장 만들기` (데스크탑·모바일 공통). 모바일은 바텀시트, 768px 이상은 가운데 대화상자(같은 컴포넌트, CSS로 전환. 대화상자는 끌어서 닫기 없음).
- **청첩장 제목** (`doc.title`, 최대 40자): 링크 공유 시 보이는 제목. 기본 정보에서는 입력하지 않는다. 비워두면 `<신랑> ♥ <신부> 결혼합니다`로 자동 생성되며(`resolveTitle`), 입력란 placeholder로 미리 보여준다. 이름을 바꾸면 자동 제목도 따라 바뀐다.
- **링크** (`doc.slug`): `<사이트 호스트>/i/<slug>`. 문서 생성 시 자동 입력 — `<예식일 YYYYMMDD>-<랜덤 4자>`(예: `20270116-k3x9`), 쉽게 시작에서 일시를 입력하면 그 날짜로 생성. 사용자가 수정 가능, `자동 링크 다시 만들기`로 새 자동 값.
  - 입력 정규화(타이핑 중): 소문자, 공백→`-`, `a-z 0-9 -` 외 제거, 연속 `-`는 하나로, 최대 40자.
  - 검증(포커스 해제·제출 시): 3자 이상, `-`로 시작/끝 불가. 오류는 입력란 아래에 표시.
  - 중복 검사는 서버 도입 후(현재 불가).
- `청첩장 만들기` 제출: 검증 통과 시 "청첩장 발행은 서버 연동 후 제공돼요" 안내(실제 발행 없음). `/i/<slug>` 하객 페이지 라우트는 아직 없다.

### §6.7 섹션 순서 변경 (드래그 앤 드롭)
- 데스크탑 섹션 목록과 모바일 `구성` 시트 공통. 각 행 우측의 손잡이(⠿)를 끌어 순서를 바꾼다. 위/아래 화살표 버튼은 두지 않는다.
- 포인터 이벤트로 구현(마우스·터치 공통, HTML5 DnD 미사용). 손잡이는 `touch-action: none`으로 스크롤과 충돌하지 않게 한다.
- 끄는 동안 다른 행이 비켜나며 들어갈 자리를 보여준다. 놓는 순간 `REORDER_SECTION`으로 반영.
- 고정 섹션(히어로·브랜드 소개)은 손잡이가 없다. 다른 섹션을 히어로 위나 브랜드 소개 아래로 놓아도 고정 자리 안쪽에 들어간다(목록과 리듀서가 함께 제한).
- 접근성: 손잡이에 포커스 후 ↑/↓ 방향키로 한 칸씩 이동.
- 숨김 상태는 표시 스위치로만 나타낸다(`숨김` 배지·항목명 줄긋기 없음).

## 제7장 저장 정책

### §7.1 v0.4: 저장 없음
- **저장·자동 저장·이어서 편집 기능을 두지 않는다.** 문서는 메모리(React 상태)에만 존재한다.
- 새로고침·탭 닫기·편집기 이탈 시 내용이 사라진다. 따라서:
  - 편집기에 문서가 있는 동안 브라우저 `beforeunload` 경고를 건다.
  - 편집기에는 뒤로/닫기 버튼을 두지 않는다(§6.5-6). 브라우저 뒤로가기로 나간 경우 내용은 사라진다.
- 같은 탭 안에서 `/editor` ↔ `/view` 이동은 내용이 유지된다.
- 저장을 다시 도입할 때는 새 PRD로 저장소(로컬/서버)·이어서 편집 UX를 정의하고 이 조항을 개정한다. (v0.1~v0.3의 IndexedDB 단일 초안 구현은 git 이력 참고)

### §7.2 이미지 정책
- 업로드 시 긴 변 **1600px**, JPEG 품질 **0.82**로 재인코딩(EXIF 회전은 브라우저 `createImageBitmap` 기본 동작에 따름).
- 허용 형식: `image/*` (HEIC는 브라우저가 디코딩 가능한 경우만).
- 1회 업로드 최대 20장, 문서당 최대 30장.

## 제8장 UI·접근성 공통 규칙

- **공통 헤더 (`AppHeader`)**: 모든 단계(템플릿·시작 방법·쉽게 시작·편집기 데스크탑/모바일)에서 상단에 고정(sticky)되며, 로고 `청첩장 메이커`는 **항상 중앙**에 보인다. 어떤 단계에서도 숨기지 않는다.
  - 단계 표시(템플릿 › 시작 방법 › 편집)는 두지 않는다.
  - 좌측: 이전 단계로 가는 `←`(시작 방법·쉽게 시작), 편집기는 `미리보기`. 템플릿 단계는 비움. 우측: 편집기는 `청첩장 만들기`.
  - 편집기 헤더에 문서 제목·저장 상태·하객 화면 보기·공유 버튼을 두지 않는다.
- 하단 고정 버튼 문구에 화살표(→)를 붙이지 않는다.

- **고딕 = Pretendard** (앱 UI·초대장 sans 공통, jsDelivr `pretendard@v1.3.9` dynamic subset). 초대장 serif 테마는 Gowun Batang(Google Fonts). 쓰지 않게 된 폰트는 즉시 뺀다(로딩 비용).
- **굵기는 세 가지만:** SemiBold **600** = 제목·헤딩(섹션 제목, `h1~h6`, `b`·`strong`, 이름) / Medium **500** = 레이블·캡션(입력 레이블, 버튼, 날짜·보조 정보) / Regular **400** = 본문. 300 이하·700 이상은 쓰지 않는다.
- **순검정(`#000000`)은 쓰지 않는다.** 가장 짙은 색은 `#151515`(글자·그림자·dim 모두, `rgba(21, 21, 21, a)`). 예외: 화면에 보이지 않는 CSS 마스크의 `#000`(모양을 뚫는 용도).
- **자간(`letter-spacing`)은 주지 않는다.** 앱 UI·초대장·장식 문구 모두 글꼴 기본 자간 그대로 쓴다.
- 터치 타깃 최소 44×44px. 모든 아이콘 버튼에 `aria-label`.
- 색만으로 상태를 표시하지 않는다(텍스트 병기).
- 초대장 본문 최대 폭 480px, 중앙 정렬 (데스크탑에서 열어도 모바일 비율 유지).
- `prefers-reduced-motion`이면 애니메이션 제거.

## 제9장 개발 규칙

### §9.1 기술 스택
React 18 + TypeScript + Vite, 라우팅 react-router-dom v6. 스타일은 CSS 파일 + CSS 변수(외부 UI 라이브러리 미사용).

### §9.2 디렉터리
```
src/
  types/        도메인 타입 (InvitationDoc 등)
  data/         기본 문서·테마 프리셋(templates.ts), 디자인 템플릿(designTemplates.ts)
  store/        편집기 상태(리듀서, 컨텍스트)
  lib/          순수 로직 (이미지 분석, 쉽게시작, 날짜, 색)
  components/
    invitation/ 초대장 렌더러 + 섹션 컴포넌트 (편집기·뷰어 공용)
    editor/     편집기 전용 UI
    common/     공용 UI
  pages/        라우트 단위 화면
```

### §9.3 커밋 메시지
```
<type>(<scope>): <한 줄 요약>

<주요 내용 — 무엇을, 왜. 글머리표 권장>

Refs: PRD-XXXX, §조항
```
- type: `feat` `fix` `docs` `refactor` `style` `chore` `test`
- 정책을 바꾸면 본문에 **바뀐 조항**과 이전→이후를 적는다.

### §9.4 문서 갱신 의무
- 정책·로직 변경 → 이 문서 해당 조항 수정 + 개정 이력 추가 (같은 커밋)
- 새 기능·흐름의 큰 재설계 → 새 PRD 스냅샷 1개 (기능 단위). 같은 기능을 다듬는 연속 수정은 PRD를 새로 쓰지 않는다(헌법 갱신 + 커밋 메시지)


### §9.5 공유용 프로토타입 빌드 (claude.ai 페이지)
- 목적: 개발자가 아닌 사람(디자인·흐름 확인용)에게 **링크 하나로** 프로토타입을 보여준다. 코드 저장소 공유가 아니다.
- 명령: `npm run build:share` → `dist-share/share.html` + `dist-share/assets/app.js`, `app.css`
  - `--mode share`(`.env.share`): `VITE_ROUTER=memory` → **메모리 라우터** 사용. claude.ai 페이지는 URL 경로(`/templates/...`)를 쓸 수 없기 때문. 로컬 개발(`npm run dev`)은 그대로 브라우저 라우터.
  - 자산은 상대 경로(`base: './'`), 파일명 고정(`app.js`/`app.css`) → 재게시 때 같은 경로를 덮어쓴다.
  - `scripts/to-artifact.mjs`가 `index.html`에서 `<!doctype>/<html>/<head>/<body>`와 charset·viewport meta를 걷어낸다(게시 시 골격이 붙으므로).
- 게시: `share.html`을 페이지로, `assets/app.js`·`assets/app.css`를 함께 게시. 같은 artifact URL에 재게시해 링크를 유지한다.
- 공개 범위: 게시본은 **비공개로 시작**하며, 공유는 소유자가 페이지의 Share 메뉴에서 직접 한다.
- 제약: 저장 기능이 없으므로(§7.1) 보는 사람마다 각자의 브라우저에서 따로 동작하며 새로고침하면 처음으로 돌아간다. 브라우저 뒤로가기는 앱 화면 이동에 쓰이지 않는다(헤더 `←` 사용). `tel:`/`sms:`/지도 앱 링크·클립보드 복사는 페이지 환경에 따라 동작하지 않을 수 있다.
- `dist-share/`는 빌드 산출물이라 git에 넣지 않는다.


### §9.6 GitHub Pages 배포 (공개 프로토타입)
- 레포: https://github.com/Ranixxd/invitation-maker (공개 — 도메인 없는 프로토타입 단계)
- 주소: **https://ranixxd.github.io/invitation-maker/** — 계정·설치 없이 누구나 열 수 있다. 친구·외부 확인용 기본 링크.
- **배포 허가 원칙:** 배포는 **사용자의 명시적 허가를 받은 뒤에만** 한다. `main` push = 즉시 공개 배포이므로, 작업 완료 후에는 로컬 커밋까지만 하고 배포 여부를 묻는다. 허가는 건별이며 이전 허가가 다음 배포에 이어지지 않는다. Actions 수동 실행도 같다.
- 배포: `.github/workflows/deploy-pages.yml` — `main`에 push될 때마다(또는 Actions 탭에서 수동 실행) `npm ci` → `npm run build:pages` → Pages 배포. 레포 Pages 설정은 "GitHub Actions" 소스.
- `npm run build:pages`(`--mode pages`):
  - `base: '/invitation-maker/'`, 라우터 `basename`도 같은 값(`import.meta.env.BASE_URL`). 로컬 개발은 `/` 그대로.
  - `scripts/spa-fallback.mjs`가 `dist/index.html`을 `dist/404.html`로 복사 → 새로고침·직접 링크(`/invitation-maker/templates/<id>` 등)에서도 앱이 뜬다(응답 코드는 404지만 화면은 정상).
- 링크 미리보기(§6.6)의 접두사는 배포 경로를 포함한다(`<호스트>/invitation-maker/i/`).
- 제약은 §9.5와 같다: 저장 없음(새로고침 시 처음으로), 각자 브라우저에서 따로 동작.
- 레포가 공개이므로 비밀값(API 키 등)을 커밋하지 않는다. 필요해지면 GitHub Actions Secrets를 쓴다.
- **배포 전 확인은 프로덕션 빌드로** 한다(`npm run build` 후 `npx vite preview`). 개발 서버는 React StrictMode가 effect를 두 번 실행해 "첫 실행에서만 생기는" 버그를 가린다(예: 부모 ref가 아직 비어 있는 자식 layout effect).
