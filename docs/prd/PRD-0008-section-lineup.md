# PRD-0008 청첩장 구성 13개로 재편

| 항목 | 내용 |
|---|---|
| 상태 | **확정 (스냅샷)** — 이 문서는 수정하지 않는다. 변경은 새 PRD로. |
| 작성일 | 2026-10-13 |
| 관련 헌법 | CONSTITUTION v0.10 (§4.1, §4.2, §4.4, §4.7~§4.9 신설, §6.5, §6.7) |
| 대체 | PRD-0001 §4.1 섹션 8종 구성 (기존 섹션 일부 유지·재정의) |

---

## 1. 배경
초기 8개 섹션(PRD-0001)은 기능 단위로 나뉘어 있었다. 실제 모바일 청첩장이 하객에게 전하는 흐름은 다음과 같다.
**누가(신랑·신부·혼주) → 어떤 사람들인지 → 언제·어디서 → 사진 → 응답(참석·축의·축하) → 찾아오기 → 마무리**

이 흐름에 맞춰 섹션을 다시 짜고, 참석 여부·게스트 스냅처럼 요즘 청첩장에서 흔한 기능을 추가했다.

## 2. 구성 (기본 순서)
| # | 섹션 | 비고 |
|---|---|---|
| 1 | 히어로 | 맨 앞 고정 |
| 2 | 시작 멘트 | 기존 인사말. 혼주 서명은 3번으로 이동 |
| 3 | 신랑·신부 | **신설.** 이름 크게, 혼주는 작게(`○○ · ○○의 아들`), 연락하기(접힘) |
| 4 | 신랑·신부 추가 정보 | **신설.** MBTI, 한 줄 소개, 타임라인 |
| 5 | 예식 일자 | 기존 날짜 + **장소 요약**(날짜·시간·장소·달력·D-day) |
| 6 | 갤러리 | 유지 |
| 7 | 참석 여부 | **신설.** 측·성함·참석/불참·인원·식사 |
| 8 | 마음 전할 곳 | 계좌, 유지 |
| 9 | 방명록 | 기존 "신랑/신부에게 할 말" → 명칭 변경 |
| 10 | 오시는 길 | 지하철·버스·자가용, 유지 |
| 11 | 게스트 스냅 | **신설.** 필요한 사람만 → **기본 꺼짐** |
| 12 | 마무리 멘트 | **신설.** "잘 살겠습니다" + 이름 서명 |
| — | 화환 | **제외.** 연계 가게(꽃집)가 필요해 로드맵으로 |
| 13 | 브랜드 소개 | **신설.** 맨 뒤 고정, 순서 변경·숨김·편집 불가 |

## 3. 결정
| # | 결정 | 이유 |
|---|---|---|
| D1 | 기존 `parents`(혼주 카드) 폐지 → `couple`로 통합, 혼주는 이름 아래 작게 | 하객이 먼저 찾는 건 신랑·신부. 혼주 정보는 보조 |
| D2 | 시작 멘트의 이름 서명 삭제 | 3번 섹션과 중복 |
| D3 | 연락처는 `couple` 섹션의 접힌 `연락하기` 안으로 | 화면을 차지하지 않게, 전화번호 넣은 사람만 노출 |
| D4 | 추가 정보는 비어 있으면 하객 화면에서 숨김 | 선택 입력 성격. 빈 섹션 노출 방지 (갤러리 §4.6과 같은 원칙) |
| D5 | 예식 일자에 장소 요약 추가 | 날짜·시간·장소를 한눈에 (상세 길안내는 10번) |
| D6 | 고정 섹션을 `hero`(맨 앞)·`brand`(맨 뒤) 둘로 일반화(`isPinned`) | 규칙 하나로 목록·리듀서·모바일 편집 버튼을 일관되게 처리 |
| D7 | 브랜드 소개가 기존 하객 화면 하단 문구(footer)를 대체 | 브랜드 노출을 섹션 규칙 안에서 관리 |
| D8 | RSVP·게스트 스냅은 서버 전까지 데모 동작 | 방명록과 같은 원칙(응답자 브라우저 저장 / 저장 안 함) |

## 4. 열린 질문
- RSVP 주최자 화면: 응답 목록·인원/식사 집계·마감일·알림
- 게스트 스냅: 공개 시점(예식 당일부터?), 장당 용량, 주최자 일괄 다운로드
- 화환: 연계 꽃집 선정, 주문·결제 흐름, 수수료 구조
- 타임라인에 사진을 붙일지
